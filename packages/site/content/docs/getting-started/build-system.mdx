## Introduction

The build copies the files of `source/<brand>/<app>/<type>/` to `dist/<platform>/<app>/<brand>/`. On the way it leaves out the formats a platform does not use, renames each file for the platform, and sorts Android image variants into density folders. It does not resize, convert or re-encode a file.

This page is the reference of the build: its commands and options, the `chassis` block that configures it, the rules of each platform, the checks that read its output, and the library behind the commands.

## Prerequisites

The build needs Node.js 22.12 or later and nothing installed: it imports Node.js modules only. Run `pnpm install` for the tests, the type check, the documentation site and the `--vector-drawables` option.

Run every command from the repository root. A clone needs its Git LFS files, see [Build fails on pointers](#build-fails-on-pointers).

## Commands

Each command is a script of the root `package.json`, and each `pnpm assets*` command prints its options with `--help`.

<CxTable>
| Command | What it does |
| --- | --- |
| `pnpm assets` | Builds every job of the configuration into `dist/` |
| `pnpm assets:site` | Builds the web output of the configured docs app for the `chassis` brand, which the Chassis sites read |
| `pnpm assets:validate` | Checks an existing output against the source and the configuration |
| `pnpm assets:contract` | Checks that an existing output has the files its consumers read by name |
| `pnpm assets:verify` | Runs the validator, then the contract check |
| `pnpm assets:lint:source` | Checks the names and the layout of `source/` |
| `pnpm assets:analyze` | Reports sizes, types, the largest files and files with the same content |
| `pnpm test` | Runs the tests of the build |
| `pnpm clean` | Removes `dist/` and the built site |
</CxTable>

### Build options

The options of `pnpm assets` select the jobs, the folders and what happens to the output that is already there.

<CxTable>
| Option | What it does |
| --- | --- |
| `--brand <name...>` | Only these brands |
| `--app <name...>` | Only these apps |
| `--platform <name...>` | Only these platforms |
| `--clean` | Remove the output first, of the selected jobs when filtered |
| `--no-clean` | Keep the output even for a full build |
| `--out <dir>` | Output folder, `dist` by default |
| `--cwd <dir>` | Repository root, by default the nearest folder upward whose `package.json` has a `chassis` block |
| `--dry-run` | Print the jobs and their file counts, write nothing |
| `--allow-lfs-pointers` | Copy Git LFS pointer files instead of failing. `CHASSIS_ALLOW_LFS_POINTERS=1` does the same |
| `--vector-drawables` | Write the SVG icons of Android as vector drawables, `.xml` in place of `.svg`. Needs `pnpm install` |
| `--asset-catalog` | Write the images of iOS as an asset catalog, `Assets.xcassets` in place of `images/` |
| `--res` | Write the fonts, images and icons of Android as a `res/` folder, `res/font/` and `res/drawable*/` |
| `--quiet` | Print errors only |
| `--help`, `-h` | Print the options |
| `--version`, `-v` | Print the version |
</CxTable>

### Filters

A filter takes one or more values, and the filters combine: the build runs the jobs that match all of them.

```bash
pnpm assets --brand chassis
pnpm assets --platform ios android
pnpm assets --brand chassis --app docs --platform web
```

A value that the configuration does not have fails the build and names the configured values. Filters that match no job together, such as an app with a platform it is not built for, fail the build too.

### Cleaning

A build without filters removes `dist/` first, so the output holds nothing of an earlier build. A build with filters keeps `dist/` and writes over the files of its jobs, so you can build one job after another.

```bash
pnpm assets                                    # removes dist/, builds every job
pnpm assets --no-clean                         # keeps dist/, builds every job
pnpm assets --brand chassis --platform web     # keeps dist/, builds the selected jobs
pnpm assets --clean --brand chassis --app docs # removes the folders of the selected jobs first
```

With filters, `--clean` removes the folders of the selected jobs only. The output of the other jobs stays.

### Vector drawables

The `--vector-drawables` option writes each SVG file under `icons/` of an Android job as a vector drawable, the format the `res/drawable/` folder of an app takes. It is off by default, and the output of every other platform and type stays as it is.

```bash
pnpm install
pnpm assets --vector-drawables
```

The file keeps its folder and its name and gets the `.xml` extension: `icons/svgs/ic_arrow_right_solid.svg` becomes `icons/svgs/ic_arrow_right_solid.xml`. A path without a fill color is filled black, which a tint replaces in the app.

The conversion is the one step of the build that uses a package, `svg2vectordrawable`, and the build loads it only with this option. Without the package the build stops before it removes anything and names `pnpm install` as the fix. An SVG without a shape, such as the SVG file of an icon font, stays an SVG and the build warns about it. A file that is not an SVG fails the build.

### Asset catalog

The `--asset-catalog` option moves the images of an iOS job from `images/` into `Assets.xcassets`, the folder Xcode reads image sets from. It is off by default, needs nothing installed, and leaves the output of every other platform and type as it is.

```bash
pnpm assets --asset-catalog
```

The files of one base name are one image set, with the `Contents.json` that Xcode writes: `images/badge.png`, `images/badge@2x.png` and `images/badge@3x.png` become `Assets.xcassets/badge.imageset/`, each file in the slot of its indicator. An SVG or a PDF without a raster of its name is an image set of one file that keeps its vector data. A subfolder of `images/` is a folder of the catalog that provides a namespace, so `images/logo/mark@2x.png` is in `Assets.xcassets/logo/mark.imageset/` and an app names it `logo/mark`.

A file without a place in an image set stays in `images/`, and the build warns once per job with the number of such files. These are an SVG or a PDF beside a raster of its name, a variant with another indicator than `@1x`, `@2x` or `@3x`, a second file for one slot, and any format but PNG, JPEG, SVG and PDF. The build does not pair a light and a dark image, and the icons of `icons/` stay files.

### Res folder

The `--res` option moves the files of an Android job that the `res/` folder of an app takes into one, `dist/android/<app>/<brand>/res/`. It is off by default, needs nothing installed, and leaves the output of every other platform as it is.

```bash
pnpm assets --res
pnpm assets --res --vector-drawables   # with the icons, needs pnpm install
```

A TTF or OTF file of `fonts/` moves to `res/font/`. A PNG, WebP, JPEG or GIF file of `images/` moves to the folder of `res/` that is named as its density folder, so `images/logo/drawable-xhdpi/mark.png` becomes `res/drawable-xhdpi/mark.png`. A vector drawable of `icons/` moves to `res/drawable/`, which makes `--vector-drawables` the option that brings the icons into `res/`.

The `res/` folder does not nest, so the subfolders of `images/` and `icons/` are dropped. When two folders hold an image of one name, the folder nearest to `images/` gets the resource with every density it has, and the files of the other folder stay.

A file without a place in `res/` stays where it is, and the build warns once per job with the number of such files. These are the font licenses, every SVG file, a second file of a name in another format, such as `text.otf` beside `text.ttf` or a WebP beside a PNG, and a name that cannot be a resource: one that starts with a digit, or a word of Java such as `default`.

## Configuration

The `chassis` block of the root `package.json` names what is built. What the checks verify is in a file of its own, see [Checks file](#checks-file).

```json
{
  "chassis": {
    "defaults": {
      "brandFolder": "default"
    },
    "build": {
      "brands": ["chassis", "example"],
      "apps": {
        "docs": ["web"],
        "demo": ["ios", "android"]
      }
    }
  }
}
```

### chassis.defaults

`brandFolder` is the name of the default brand in `source/`, the folder whose files every brand gets. It is `default` unless the block says otherwise.

### chassis.build

`brands` and `apps` name the folders of `source/` that the build reads and the folders of `dist/` that it writes.

<CxTable>
| Key | Type | Meaning |
| --- | --- | --- |
| `brands` | Array of strings | The brands to build. A brand needs no folder in `source/`: without one it gets the default files |
| `apps` | Object | Each app, with the array of platforms it is built for: `web`, `ios`, `android` |
</CxTable>

### Jobs

A job is one brand, one app and one platform. The build runs every brand for every platform of every app, and writes each job to `dist/<platform>/<app>/<brand>/`, the layout that Chassis Tokens uses too.

In the `chassis` block of `package.json`, two brands and two apps:

```json
{
  "chassis": {
    "build": {
      "brands": ["acme", "wonka"],
      "apps": {
        "website": ["web"],
        "mobile": ["ios", "android"]
      }
    }
  }
}
```

The build of this configuration writes these folders:

```text
dist/web/website/acme/
dist/web/website/wonka/
dist/ios/mobile/acme/
dist/ios/mobile/wonka/
dist/android/mobile/acme/
dist/android/mobile/wonka/
```

## Platform rules

Each platform has a processor that says which formats it keeps and how a file is named. The rules of a type apply to the files of its folder, `fonts/`, `images/` or `icons/`, and any other folder is copied in every format.

<CxTable>
| Rule | Web | iOS | Android |
| --- | --- | --- | --- |
| Names | kebab-case | snake_case | snake_case |
| Indicator `@2x`, `@3x` | Kept in the name | Kept in the name | Removed from the name |
| `fonts/` | WOFF, WOFF2, CSS, SCSS, TXT | TTF, OTF, TXT | TTF, OTF, TXT |
| `images/` | Every format | Every format but WebP. An asset catalog with `--asset-catalog` | Every format, in density folders. In `res/` with `--res` |
| `icons/` | Every format | SVG, PDF, PNG | SVG, with the `ic_` prefix. Vector drawables with `--vector-drawables` |
| Subfolders | Kept | Kept | Kept, with the density folders inside each |
</CxTable>

The pages of the [fonts]([[docsref:/asset-types/fonts#platform-output]]), the [images]([[docsref:/asset-types/images#platform-output]]) and the [icons]([[docsref:/asset-types/icons#platform-output]]) show the output of each type.

### Renaming

A name is lowercased, and every space, underscore, dot inside the name or other character becomes the separator of the platform: a hyphen for the web, an underscore for iOS and Android. `Hero Banner@2x.png` is `hero-banner@2x.png` for the web and `hero_banner@2x.png` for iOS.

When two files of a folder get the same name on a platform, the file copied last wins, and the build warns with `Filename collision: "<name>" → "<new name>" (conflicts with "<other name>")`. A brand file over the default file of the same name is the override, not a collision. Names that keep the rules of the [design guidelines]([[docsref:/getting-started/design-guidelines]]) do not collide.

### Ignored files

The build does not copy the files that an operating system or an editor leaves behind: `.DS_Store`, `Thumbs.db`, `desktop.ini`, `.gitkeep`, and names that match `._*`, `*~`, `*.swp`, `*.tmp` or `*.temp`. It removes a folder that is empty after the format rules.

## Checks

The checks read `source/` or an existing output and change nothing. Each exits with 1 when it fails, so a script or a CI job stops there.

### Validator

`pnpm assets:validate` checks an existing output against the source and the configuration. Run it after a full build.

```bash
pnpm assets
pnpm assets:validate
```

It checks that the output and the source exist, that every job has its folder and the type folders of its source, that every source file is there under the name of the platform, that the output has no fewer files than the source and no empty folder, and that the names keep the rules of the platform. `--out <dir>` reads another folder than `dist/`.

### Contract check

A contract is a list of files that a consumer reads by name from the output of one job. `pnpm assets:contract` checks the contracts of `chassis.checks.json`, and names each missing file and its reader.

```bash
pnpm assets:contract
pnpm assets:verify
```

`pnpm assets:verify` runs the validator and then the contract check. A repository without contracts has nothing to check, and the command is the validator alone.

### Source lint

`pnpm assets:lint:source` checks `source/` against the naming rules of the [design guidelines]([[docsref:/getting-started/design-guidelines]]).

It fails on a name or a folder that is not of lowercase letters, digits and hyphens, on an indicator that is not at the end of a name, on an extension with capitals, on a file outside a type folder, and on a Git LFS pointer in place of a file. It warns about a brand or an app folder that the configuration does not name, which the build does not read.

The message suggests a name that keeps the rules. A file that breaks a rule on purpose is listed in `lint.allow` of the checks file with the reason, and is printed as a warning.

### Analyzer

`pnpm assets:analyze` reports on `source/` and on an existing output: the file types, the files per platform, brand and app, the largest files, and the files with the same content. It takes the filters of the build.

```bash
pnpm assets:analyze
pnpm assets:analyze --brand chassis --platform web
```

Files with the same content are listed per group, for the source and for the output apart. An app that holds a copy of the files of another app, as `docs` and `demo` of this repository do, shows up there.

## Checks file

What the checks verify is in `chassis.checks.json`, beside `package.json`. The build does not read it. The file is optional: without it there is no contract to check and no name that the source lint keeps.

### contracts

`contracts` holds, for a job written as `<platform>/<app>/<brand>`, the files that a consumer reads by name from its output.

<CxTable>
| Key | Type | Meaning |
| --- | --- | --- |
| `reader` | String | Who reads the files, printed when one is missing |
| `files` | Array of strings | Paths that have to be there, relative to the output of the job. `{a,b}` stands for each alternative |
| `sets` | Array | Patterns of files that are read together, with `*` and `{a,b}`. When the output has a file that matches, it has to have that file with every other alternative too. An entry is a pattern, or an object with `pattern` and `except`, a list of patterns to leave out |
</CxTable>

In `chassis.checks.json`, a contract with a list of files and a set:

```json
{
  "contracts": {
    "web/docs/chassis": [
      {
        "reader": "the layout of the site",
        "files": ["images/site-logo.svg", "images/favicon{,-16x16,-32x32}.png"]
      },
      {
        "reader": "the gallery of the site",
        "sets": ["images/gallery/*/{light,dark}/*{,@2x}.png"]
      }
    ]
  }
}
```

The set says that every image of the gallery is there in the light and in the dark mode, each at the base size and at `@2x`.

### lint.allow

`lint.allow` lists the files of `source/` that break a naming rule and are kept. The source lint prints a warning for them instead of an error.

<CxTable>
| Key | Type | Meaning |
| --- | --- | --- |
| `pattern` | String | The path of the file, relative to `source/`, with `*` for one folder |
| `reason` | String | Why the name is kept, printed with the warning |
</CxTable>

In `chassis.checks.json`, the entry of a file that another project names:

```json
{
  "lint": {
    "allow": [
      {
        "pattern": "*/*/icons/icons/chassis-icons.min.css",
        "reason": "part of the build output of @chassis-ui/icons, copied as it is"
      }
    ]
  }
}
```

## Custom platforms

A platform is a processor: a module of `packages/assets/build/processors/` with the formats the platform keeps and a function that names a file. To add a platform, write the module, add it to the registry, and name the platform in an app.

Add the processor as `packages/assets/build/processors/desktop.js`. A format list that is missing means every format.

```js
const desktopProcessor = {
  name: 'desktop',
  icon: '🖥️',

  allowedFontFormats: ['.ttf', '.otf', '.txt'],
  allowedIconFormats: ['.svg'],
  excludedImageFormats: [],

  renameFile(fileName) {
    return fileName.toLowerCase()
  }
}

export default desktopProcessor
```

Add it to the registry in `packages/assets/build/processors/index.js`:

```js
import desktopProcessor from './desktop.js'

export const platformProcessors = {
  web: webProcessor,
  ios: iosProcessor,
  android: androidProcessor,
  desktop: desktopProcessor
}
```

Name the platform in an app of the `chassis` block, and build it with `pnpm assets --platform desktop`.

A processor may also place an image itself with `processImage()`, as the Android processor does for the density folders. It returns `true` when it wrote the file, and `false` to let the build copy it. Such a processor also has `imageFolder(fileName)`, which returns the folder the image goes to, so that the build can warn about two images that meet there.

A processor with `vectorDrawables` takes part in the `--vector-drawables` option. The property names the type folder and the two extensions, as the Android processor does with `{ type: 'icons', from: '.svg', to: '.xml' }`. A processor with `assetCatalog` takes part in the `--asset-catalog` option. The property names the type folder and the folder of the catalog, as the iOS processor does with `{ type: 'images', name: 'Assets.xcassets' }`. A processor with `res` takes part in the `--res` option. The property names the folder, and for the fonts and the drawables the type folders, the folder of `res/` and the formats it takes.

## Library

The commands are thin entries over modules that a script can import. An imported function takes its options as an object, never reads the command line, and throws where the command would exit.

Use the paths of your checkout. This script builds one job into a folder of its own and reads the result:

```js
import ChassisAssets from '../chassis-assets/packages/assets/build/api/index.js'
import AssetAnalyzer from '../chassis-assets/packages/assets/build/analyze-assets.js'
import { generateAssets } from '../chassis-assets/packages/assets/build/build-assets.js'

// The repository root: where package.json and source/ are
const cwd = new URL('../chassis-assets/', import.meta.url).pathname

// The build, with the options of the command line. Throws on an unknown brand
const result = await generateAssets({
  brands: ['chassis'],
  apps: ['docs'],
  platforms: ['web'],
  cwd,
  out: 'dist',
  quiet: true
})
console.log(result.filesProcessed, result.jobs)

// The configuration as an object
const assets = new ChassisAssets('package.json', { cwd })
console.log(assets.getBrands(), assets.getCombinations())

// The analyzer. analyze() is synchronous
const analyzer = new AssetAnalyzer({ brands: ['chassis'], platforms: ['web'], cwd, quiet: true })
analyzer.analyze()
console.log(analyzer.stats.totalFiles, analyzer.stats.duplicatesInSource.length)
```

### generateAssets

`generateAssets(options)` of `build-assets.js` is the build. It resolves to the statistics of the run, with `filesProcessed`, `filesRenamed`, `filesConverted`, `imageSets`, `resourceFiles`, `warnings` and `jobs`, and throws on a failure. Its options are `brands`, `apps`, `platforms`, `clean`, `quiet`, `cwd`, `out`, `dryRun`, `allowLfsPointers`, `vectorDrawables`, `assetCatalog` and `res`.

### ChassisAssets

`new ChassisAssets(configPath, { cwd, out })` of `api/index.js` reads the configuration of `package.json` in `cwd`.

<CxTable>
| Method | Returns |
| --- | --- |
| `getBrands()` | The configured brands |
| `getApps()` | The names of the configured apps |
| `getPlatforms(app)` | The platforms of one app |
| `getAllPlatforms()` | Every platform that an app names |
| `getCombinations()` | Every job, as brand, app and platform |
| `assetsExist(brand, app)` | Whether the source has files for the brand and the app |
| `getAssetInventory(brand, app)` | The source files of the brand and the app, by type |
| `build(options)` | The result of `generateAssets()` with `brands`, `apps`, `platforms`, `clean`, `quiet`, `vectorDrawables`, `assetCatalog` and `res` |
| `getStats()` | The numbers of brands, apps, jobs, source files and output files |
| `validate()` | The errors and the warnings of the configuration and the source |
</CxTable>

### AssetAnalyzer

`new AssetAnalyzer({ brands, apps, platforms, quiet, cwd, out })` of `analyze-assets.js` takes the filters and the folders. `analyze()` fills `stats`: `totalFiles`, `totalSize`, `fileTypes`, `platforms`, `brands`, `apps`, `largestFiles`, `duplicatesInSource` and `duplicatesInDist`. `formatBytes(bytes)` formats a size for reading.

## Continuous integration

A CI job builds the output it needs and checks it. The checkout has to fetch the Git LFS files, and the build needs no install step.

```yaml
name: Assets

on: [push, pull_request]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
        with:
          lfs: true

      # pnpm at the version of packageManager, Node.js from .nvmrc
      - uses: pnpm/action-setup@v6
      - uses: actions/setup-node@v7
        with:
          node-version-file: .nvmrc

      - name: Lint the source
        run: pnpm assets:lint:source

      - name: Build
        run: pnpm assets

      - name: Verify
        run: pnpm assets:verify
```

To build one platform per job, give each job a filter, such as `pnpm assets --platform ios`, and keep its folder, `dist/ios/`. A job that needs the names and not the binaries, such as the source lint alone, can skip the Git LFS files and pass `--allow-lfs-pointers`.

## Tests

The tests run with [Vitest](https://vitest.dev/) on a small fixture in `packages/assets/test/fixtures/`, with brands, apps and files of its own. They need no Git LFS files and write to temporary folders only, never to `dist/`.

```bash
pnpm test           # run every test
pnpm test:golden    # write the golden output again
```

One test builds the fixture and compares the result, file by file, with the committed output in `packages/assets/test/golden/`. After a change to the build that is meant to change the output, run `pnpm test:golden` and review the difference: every file that moves or changes its name there does so in `dist/` too.

## Best practices

✅ **Build a part while you work:** `pnpm assets --brand chassis --platform web` writes one job and keeps the rest of `dist/`.

✅ **Run a full build before the checks:** `pnpm assets:validate` and `pnpm assets:verify` expect the output of every job.

✅ **Start with the default brand:** put a complete set of files in `source/default/<app>/`, and add to a brand folder only what differs.

✅ **Keep brand and app names in lowercase with hyphens:** they are folder names in `source/` and in `dist/`, and a consumer reads its files by that path.

❌ **Do not commit `dist/`:** every consumer builds it from the source.

❌ **Do not rename a brand or an app without telling the consumers:** the name is part of every path of its output.

## Troubleshooting

### Build fails on pointers

The build stops with `<count> source file(s) are Git LFS pointers, not files: <files>`. The clone has no Git LFS files, so a font or an image is a pointer of a few lines. Install Git LFS, run `git lfs pull`, and build again. Pass `--allow-lfs-pointers` only where the binaries are not needed.

### Unknown brand

The build stops with `Unknown brand "<name>". Configured: <names>`, or the same for an app or a platform. A filter has a value that the `chassis` block does not name. Use a name of the list.

### No job selected

The build stops with `The filters select no job. Check --brand, --app and --platform together.` Each value is configured, and no app has that platform. Run `pnpm assets --dry-run` to see the jobs.

### Validator misses files

`pnpm assets:validate` fails after a filtered build and names the folders or the files of other jobs. The validator checks every job of the configuration. Run `pnpm assets` without filters, then validate.
